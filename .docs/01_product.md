# プロダクトページ設計

> 上位の思想は [`00_manifesto.md`](./00_manifesto.md) に記載。設計判断はマニフェストに従う。

## コンセプト

**プロダクトの技術スタックをエンジニア視点で公開する場所。**

評価軸は持たない。いいね・星・ランキングは存在しない。**ジャッジレス** であることが、エンジニアが安心して自分の作品を載せる前提になる。

Zenn/Qiita のような技術記事でも、Wantedly のような採用ナラティブでも、LinkedIn のような職歴SNSでもない。プロダクトの **技術構成そのもの** を構造化された共通フォーマットで世に出す。

## 他サービスとの違い

```
Zenn/Qiita   → 自由記述の技術記事。構造化されていない
Wantedly     → 採用目線。「いい会社です」止まりで技術の深さがない
GitHub       → コードは見れるが、なぜその技術を選んだかは分からない
StackShare   → 技術リストだけ。背景もストーリーもない、しかも誰も書かない
LinkedIn     → 「○○社で働いてました」だけ。技術の深さゼロ

Quine      → プロダクトの技術構成が構造化されている (透明性)
             → プロダクト × エンジニア個人の視点が紐付いている
             → 評価軸を持たない (ジャッジレス)
```

## 親子構造

### 概要

```
プロダクト（親）
  → プロダクト全体の情報。作成者が管理。開発者全員で共有。
  → 開発者一覧が表示され、各開発者の詳細に遷移できる。

開発者の参加情報（子）
  → 各エンジニアが自分の担当・エピソードを書く。
  → 親の概要・技術スタックは共有。それ以外は各自が記述。
```

## プロダクト（親）の項目

### 基本情報

| 項目 | 形式 | 必須 | 説明 |
|------|------|------|------|
| プロダクト名 | テキスト | 必須 | |
| 一言説明 | テキスト | 必須 | 何をするプロダクトか |
| URL | URL | 任意 | GitHub / HP / なんでも。あればAIが情報を先に埋める |

### 技術スタック（レイヤー別）

**「どの層に何を使っているか」だけをシンプルに。詳細なスタック図は作らない。**

```
Frontend:   [Next.js] [React] [TypeScript] [Tailwind CSS]
Backend:    [Go] [gRPC] [PostgreSQL]
Infra:      [AWS ECS] [Terraform] [GitHub Actions]
Data:       [BigQuery] [dbt]
Monitoring: [Datadog] [Sentry]
```

選択式。technologies.type.ts の600+技術から選ぶ。
レイヤーは technologies.type.ts のカテゴリに対応。

**シンプルにする理由:**
- 嘘がつけない（使ってるか使ってないかだけ）
- 全プロダクト同じフォーマット → 一瞬で比較できる
- 作るのが簡単 → 選ぶだけ
- 古くならない（技術変えたら差し替えるだけ）

### アーキテクチャ

| 項目 | 形式 | 必須 |
|------|------|------|
| 構成タイプ | 選択式 | 任意 |

選択肢: モノリス / マイクロサービス / サーバーレス / モジュラーモノリス / etc.

### 技術的な意思決定

| 項目 | 形式 | 必須 |
|------|------|------|
| なぜこの構成にしたか | 自由記述 | 任意 |

例:
- 「SPA → SSRに移行した理由」
- 「RailsからGoに書き換えた背景」
- 「モノリスからマイクロサービスへの移行判断」

### 開発体制

| 項目 | 形式 | 必須 |
|------|------|------|
| エンジニア人数 | 数値 or 選択 | 任意 |
| チーム構成 | テキスト | 任意 |
| 開発手法 | 選択式 | 任意 |

開発手法の選択肢: スクラム / カンバン / XP / ウォーターフォール / etc.

### 規模感

| 項目 | 形式 | 必須 |
|------|------|------|
| ユーザー規模 | 選択式 | 任意 |
| デプロイ頻度 | 選択式 | 任意 |

ユーザー規模: 〜1K / 〜10K / 〜100K / 100K+
デプロイ頻度: 日次 / 週次 / 隔週 / 月次 / etc.

### 技術的ハイライト

| 項目 | 形式 | 必須 |
|------|------|------|
| 技術的に面白い部分 | 自由記述 | 任意 |
| 一番大変だった技術的課題 | 自由記述 | 任意 |

## 開発者の参加情報（子）の項目

### 親から共有（自動表示、編集不可）

- プロダクト名
- 概要
- 技術スタック（レイヤー別）

### 個人が記述する項目

| 項目 | 形式 | 必須 | 説明 |
|------|------|------|------|
| 担当領域 | 選択式 | 必須 | 親の技術スタックのレイヤーから選択 |
| 担当技術 | 選択式 | 必須 | 親の技術スタックから選択 |
| ポジション / 役割 | テキスト or 選択式 | 必須 | テックリード / メンバー / etc. |
| 参加期間 | 期間 | 任意 | |
| エピソード | 自由記述 | 任意 | 自分なりの体験・ストーリー |
| 技術的ハイライト | 自由記述 | 任意 | 自分が担当した技術的に面白い部分 |

### 同じプロダクトでも人によって見え方が違う

```
田中（バックエンド / テックリード）:
  担当技術: [Go] [gRPC] [PostgreSQL]
  「RailsからGoに移行するとき、gRPCの設計で3ヶ月悩んだ」

佐藤（フロントエンド）:
  担当技術: [Next.js] [React] [TypeScript]
  「Next.js App Routerへの移行でSSRの設計を全部見直した」

鈴木（SRE）:
  担当技術: [AWS ECS] [Terraform] [GitHub Actions]
  「ECSへの移行でダウンタイムゼロのデプロイを実現した」
```

→ 1つのプロダクトに複数のエンジニアの物語がある。

## プロダクト作成フロー

### AIアシスト

チャットボット型のAIが横にいて、会話しながらフォームを埋めていく。
Claude Codeのように、チャットの結果がUIのフォームに反映される。

```
入力方法（どれでもOK、組み合わせ自由）:
  ・URLを貼る（GitHub / HP / テックブログ / 求人ページ / 画像）
  ・AIと対話して情報を引き出す
  ・手動で入力する

URLがある場合:
  → GitHub URL → GitHub API で詳細解析
  → その他URL  → AIがページを読んで技術情報を抽出
  → フォームに自動入力 → ユーザーが確認・カスタマイズ

URLがない場合:
  → AIが対話で引き出す
  → 「メイン言語は？」→ 選ぶと関連技術を提案
  → 「どんな構成？」→ モノリス/マイクロサービス等から選ぶ
  → 「インフラは？」→ AWS/GCP等を選ぶと関連サービスを提案
  → フォームに反映

どちらでも最終的な体験とクオリティは同じ。
URLは「初期値を埋めるブースト」であって、必須ではない。
```

### 自由記述のAI補助

エピソードや技術的ハイライトの自由記述部分:
- AIが技術スタックと担当領域から下書きを生成
- ユーザーが編集・肉付け
- リライト・改善提案もAIが行う

## エンジニア向け説明文のトーン

**会社のHPにはない、エンジニアが本当に知りたい情報。**

```
❌ HP的な説明:
「AIを活用した次世代マッチングプラットフォーム」

✅ Quineでの説明:
「Next.js 14 App Router + Python FastAPIのマイクロサービス構成。
 推薦エンジンはPyTorch + Transformerベースで構築。
 AWS ECS上でGitHub ActionsによるCI/CDパイプラインで運用。
 フロントはTailwind CSS + Framer Motionで構築」
```

## 開発者の参加フロー

```
1. 既存プロダクトを検索 or URLで共有される
2. 「このプロダクトの開発者として参加」ボタン
3. 親の作成者が承認（or 自動承認の設定も可能）
4. 子の項目を記入（担当領域、エピソード等）
5. 親のページの開発者一覧に表示される
```
