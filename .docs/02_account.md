# アカウントとコラボレーション設計

> 上位の思想は [`00_manifesto.md`](./00_manifesto.md) に記載。「会社と個人の境を消す」はマニフェスト由来。

プロダクトに複数ユーザーが紐付くときの扱い方、および「会社/個人」の区別をやめる方針をまとめる。

関連: `01_product.md` の親子構造をそのまま踏襲する。

---

## 1. アカウントモデル

### 原則

**Quine には「会社アカウント」「個人アカウント」の区別を設けない。すべて「ユーザー」として扱う。**

- 会社を表したい人は、会社用の GitHub で OAuth して、表示名を会社名にして登録するだけ
- Quine 側にアカウント種別フラグを持たない
- UI にも「あなたは個人ですか会社ですか」を聞く画面を出さない

### なぜこの方針か

- **設定は最小限、自動化を最大化する** という Quine の原則に従う
- アカウント種別による UI・フォームの分岐が発生しないので実装がシンプル
- GitHub 側で User と Organization は既に区別されている。Quine で二重管理しない
- フォームの項目構成はアカウント種別ではなく「そのプロダクトがどういう性格か」で決まるべき（AI が文脈でサジェストする）

### 将来やるかもしれないこと（MVPではやらない）

- 会社アカウントの検証・公式バッジ
- Organization 単位のメンバー管理
- ドメイン認証による所属会社の自動判定

これらは必要になったタイミングで追加する。今は考えない。

## 2. プロダクトへの複数ユーザー参加

### やりたいこと

- ユーザー A が作ったプロダクト A に、ユーザー B を招待できる
- プロダクト A に A と B の両方が紐付く
- B には B の Role / エピソード / 個人ハイライトがあり、A のものとは別
- でも Title / Tech Stack / Description などは A と B で同じものを共有したい
- 親子関係は維持したい

### UX の課題

B が自分の参加情報を編集するとき、プロダクト A 全体を「いじっている感覚」になるのは避けたい。
B は自分のレイヤーを編集しているのであって、A の共有情報を書き換えているわけではない、と分かる UI にする。

---

## 3. 解決方針: ベースレイヤー + 個人レイヤー

プロダクトを **「共有ゾーン」** と **「あなたのゾーン」** の 2 層に分ける。

```
┌──────────────────────────────────────────┐
│  Product A                                │
│                                          │
│  ┌─ 🌍 Shared（全員で共有・共同編集）──┐  │
│  │  Title / Tagline                   │  │
│  │  Tech Stack (レイヤー別)            │  │
│  │  Project Type / URL                │  │
│  │  Description / Architecture        │  │
│  │  Team / Scale                      │  │
│  │  Contributors: 👤A 👤B ...         │  │
│  └────────────────────────────────────┘  │
│                                          │
│  ┌─ 👤 Your perspective（自分だけ）──┐  │
│  │  Your role                         │  │
│  │  Your episode                      │  │
│  │  Your technical highlights         │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
```

### Perspective switcher

編集画面の上部にトグルを置き、今どちらを編集しているかを常に明示する。

- `🌍 Shared` を選んだとき: 共有項目のみが編集可能。ヘッダーに「この内容はコントリビューター全員に反映されます」と小さく出す
- `👤 Your perspective` を選んだとき: 自分の参加情報だけが編集可能。ヘッダーに自分のアバターを色付きで表示。背景トーンも変えて「自分の領域」であることを視覚的に強調

### 招待された B を開いたときの初期状態

- B が招待リンクから入ったら、最初は `👤 Your perspective` タブが開く
- 上部に共有情報が参照表示される（読み取り専用のサマリー）
- → いきなり A の共有情報をいじる画面にはならず、「まずは自分の参加情報を書く」に自然に誘導される

### 表示側（閲覧画面）

- プロダクトページに行くと、共有情報 + コントリビューター一覧が出る
- コントリビューターをクリックするとその人の「個人の記述」にジャンプ（親ページ内のアンカー or 子ページ）
- 同じプロダクトでも人ごとに物語が違う、が見える

## 4. データ構造

**プロダクトをコピーする必要はない。親子 2 テーブルで表現する。**

### products（親・共有）

1 プロダクト 1 レコード。共有項目をすべてここに持つ。

| カラム | 型 | 説明 |
|--------|-----|------|
| id | uuid | PK |
| created_by | uuid | 作成者（users.id） |
| title | text | |
| tagline | text | |
| project_type | text | |
| tech_stacks | text[] or 別テーブル | レイヤー別 |
| url | text | |
| description | text | |
| architecture | text | |
| team_size | int | |
| scale_users | text | |
| ... | | 共有する項目はすべてここ |

### product_members（子・個人）

1 プロダクト × N ユーザー。参加するユーザーごとに 1 レコード。

| カラム | 型 | 説明 |
|--------|-----|------|
| id | uuid | PK |
| product_id | uuid | → products.id |
| user_id | uuid | → users.id |
| role | text | 役割 |
| my_episode | text | 個人のエピソード |
| technical_highlights | text | 個人視点のハイライト |
| period_from / period_to | date | 参加期間 |
| status | text | `invited` / `active` / `declined` |
| invited_by | uuid | 招待した人 |
| joined_at | timestamp | |

UNIQUE(product_id, user_id)

### この設計で実現できること

- **コピー不要**: products は 1 レコードなので、複数人いても情報が重複しない・矛盾しない
- **親子関係を維持**: products が親、product_members が子
- **B の編集は自分の product_members 行のみ**: A の Role には一切影響しない
- **A が Title を変えれば全員に反映**: 共有なので当然そうあるべき
- **3 人目、4 人目が来ても product_members に追加するだけ**

### よくある疑問への回答

**Q. 共有する項目を B が選べるようにする必要は？**
→ 不要。共有項目は products の列として固定、個人項目は product_members の列として固定する。B が決めるのは「自分の個人項目に何を書くか」だけ。

**Q. 会社のプロダクトは Team/Scale を書くが個人はそうでもない、みたいな可変性は？**
→ 列は全部持っておき、埋めるかどうかをユーザーが決める。アカウント種別で出し分けはしない。AI が「このプロダクト会社っぽいから Team も書くと良いよ」と文脈でサジェストする程度。

**Q. 共有情報の編集競合は？**
→ 将来課題。MVP では「最後に保存した人勝ち」で十分。将来的には Figma / Notion 的な「誰が最後に編集したか」の表示、簡易ロック、編集履歴、でカバーする。

## 5. 参加フロー

```
1. A がプロダクトを作る
   → products に 1 レコード
   → product_members に A の行（status=active, role=creator 相当）

2. A が B を招待
   → product_members に B の行（status=invited）
   → B に通知 or 招待リンク

3. B が招待を受諾
   → product_members の B の行を status=active に
   → B に Your perspective 画面が開く
   → B は自分の role / episode などを記入

4. プロダクトページには A と B の両方がコントリビューターとして表示
   → 各自の個人記述に飛べる
```

### 権限

| アクション | Creator (A) | Member (B) |
|-----------|-------------|------------|
| products の編集 | ○ | ○（共同編集） |
| 自分の product_members 編集 | ○ | ○ |
| 他人の product_members 編集 | × | × |
| 新規メンバー招待 | ○ | △ (設定次第) |
| メンバー削除 | ○ | × |
| プロダクト削除 | ○ | × |

---

## 6. 設計原則まとめ

- アカウント種別を持たない。全員ユーザー
- プロダクトの「共有」と「個人」を **2 テーブル + Perspective switcher UX** で分離
- コピーしない。1 プロダクト = products に 1 行
- 親子関係は `products` ↔ `product_members` で素直に表現
- フォームはアカウント種別で分岐しない。AI が文脈で補助する
